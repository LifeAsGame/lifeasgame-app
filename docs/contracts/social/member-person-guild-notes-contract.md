## Identity and workflow

`groupType` is `GUILD`, `PARTY`, or `ROLE_PARTY`; `groupId` is that group's ID. Member `playerId` is a Player ID. `Person.linkedUserId` is a User ID, resolved server-side through `PlayerLookupApi.findUserIdByPlayerId` only after both the authenticated actor and target are current active group members. A public search result, personal Role bookmark, pending invitation, departed member, or disbanded group gives no authority. All endpoints use the authenticated current Player as owner; no owner ID or linked User ID is accepted. A Person is a private address book record; linking does not edit the target account.

1. `GET /api/v1/member-person-links?groupType=GUILD&groupId=1&memberPlayerId=2` returns `{groupType,groupId,memberPlayerId,personId,personStatus}` inside `ApiResponse.result`. `personId` and `personStatus` are null if there is no link. GET never creates or restores a Person. An archived match is reported as `ARCHIVED` and cannot be linked.
2. `PUT /api/v1/member-person-links` with `{groupType,groupId,memberPlayerId,personId}` explicitly selects an existing owned ACTIVE Person. `personId` must be unlinked or linked to this same User. The result is the same identity shape with `personStatus:"ACTIVE"`. Same request is idempotent. A Person linked to another User, or another Person already linked to this User, yields 409 without changing either. No existing profile, common notes, or role notes are overwritten.
3. `POST /api/v1/member-person-links` with `{groupType,groupId,memberPlayerId,displayName,notes?,birthday?,contact?,profile?}` creates an owned Person and links it in one transaction. `displayName` is a user-confirmed 1–80 character value; no private account fields are copied. If an owned Person is already linked to the resolved User, return that Person's ID as an idempotent result when ACTIVE; archived match returns 409. A stable owner lock and the existing `(owner_player_id,linked_user_id)` unique key serialize competing requests. A failed create rolls back fully; a retry reads the winner in a new transaction. A competing existing-Person selection returns 409 instead of silently reusing the other Person.
4. `DELETE /api/v1/persons/{personId}/linked-user` clears only the owner's current link, preserving Person, RoleRelation, and private Guild note history. Relinking another member requires a separate explicit selection. Historical Guild notes keep their original target Player ID and do not move.
5. After a successful Person step, call the **existing** `POST /api/v1/roles/{roleId}/relations` with `{personId,relationType,roleNotes}`. This is a separate command. Its existing ownership/ACTIVE rules and duplicate 409 apply; it does not overwrite an active relation or automatically restore an archived one. If it fails, the FE retains `personId` and retries this relation command alone. No group bookmark, GuildGroupLink, event, LifeLog, reward, or membership is created by linking.

Errors use the existing `ApiResponse` error envelope: group or member unavailable/foreign → 404 social code; foreign Person → `PER-404-NOT-FOUND`; archived Person → `PER-409-ARCHIVED`; conflicting link → 409 Person code; invalid body/page → 400. These endpoints return one object, not a page. Optional profile fields follow the existing Person create contract; omitted and null mean absent. IDs are distinct domain identifiers even if numbers coincide.

## Private Guild notes

The record key is `(authorPlayerId,guildId,targetMemberPlayerId)` with a fixed `personId` at creation and a DB unique key. This prevents two Guilds' notes merging or a later Person relink silently retargeting history. Only text is supported: null, omitted, or blank trims to empty and clears the note; nonblank is trimmed and capped at 2000 characters. No common Person notes, RoleRelation.roleNotes, public member DTO, or STOMP payload is changed.

- `GET /api/v1/guilds/{guildId}/members/{memberPlayerId}/my-note`: author's existing note, or 404. Current actor and target membership are required for live group context; historical reading uses the Person route below.
- `PUT /api/v1/guilds/{guildId}/members/{memberPlayerId}/my-note` with `{personId,text,version?}`: creates or replaces the author's note. Create requires owned ACTIVE Person linked to that target User; update requires the same stored Person and `version` matching the stored optimistic version. Actor and target must both be current active Guild members. Response `{id,personId,guildId,targetMemberPlayerId,text,version,availability,guildName}`. Repeated identical create returns the existing row; conflicting create/update returns 409. `guildName` is shown only while the actor has current Guild access.
- `DELETE /api/v1/guild-notes/{noteId}`: author only, 204; may delete history after departure/Person archive without changing Person, relation, or Guild.
- `GET /api/v1/persons/{personId}/guild-notes?page=0&size=20&guildId=&includeHistory=true`: author-owned notes for that owned Person, ID descending, `{contents,page,size,totalElements,totalPages}` in `ApiResponse.result`. `includeHistory=false` filters to current accessible Guilds; default includes history. An inaccessible/disbanded Guild item has `availability:"HISTORY"`, `guildName:null`, and only stored `guildId`/target ID as context; it never reloads PRIVATE Guild details or member lists. Current access has `availability:"CURRENT"` and may show the current Guild name. Foreign note or Person is hidden with 404.

New write and edit lock the Guild row and recheck both memberships before commit. Note rows have an optimistic version; stale edits return 409. Person unlink does not alter stored note ownership or target. Queries are paged in SQL, including filters and stable order; Guild names are loaded only for currently authorized page items. The Person detail and role-context endpoints stay independent.
